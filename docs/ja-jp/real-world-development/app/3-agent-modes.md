プロジェクトに小さな機能を追加しました。より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント駆動の開発プロセスを実践します。issue から新機能を作り、コードの妥当性と機能の動作を確認して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使いますが、ここでは中心的な概念に集中できるように手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増えたため、訪問者がゲームをカテゴリと発行者で絞り込めるようにします。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法などはコーディング前に合意が必要です。Plan モードで判断を整理してから、Autopilot による範囲を限定した実装を承認します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れに従います。

1. 必要な作業の詳細が記載された issue を開きます。
2. 構築する内容の計画を作成します。
3. コードを構築してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. pull request (PR) を作成します。
7. コードレビューと継続的インテグレーションプロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものになります。

この標準的な方法を守ることで、AI が生成したコードが要件を満たし、人間が作成したコードと同じレビュー工程を通るようにできます。

## セッションモード

**セッションモード**は、エージェントがどこまで自律的に作業するかを制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive:** エージェントと一緒に作業します。エージェントは変更を提案し、次に進む前に入力を待ちます。
- **Plan:** エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot:** エージェントが完全に自律して作業し、入力を待たずにコードを書き、テストを実行して反復します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリのフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる issue です。新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチを確認できます。issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、issue の受け入れ条件と計画を照らし合わせます。カテゴリと発行者による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数のカテゴリをどのように組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを終えるまで PR を作成しません。計画の修正は承認前に依頼し、後の検証に使えるよう issue の URL と合意した追加の取り決めを控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認するとモードも切り替わると決めつけず、実際のモードを確認してください。表示が **Autopilot** になっていることを確認します。

Copilot は実装を開始し、計画に沿ってコードを生成してテストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まることがあるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、他のコードと同様にマージ前にレビューします。コードを確認し、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと発行者の組み合わせも含め、結果を issue と承認した追加の取り決めに照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンのサーバーではなく、この worktree のものであることを確認してください。

## 新機能を試す

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザーキャンバスで開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターを解除してから発行者を選択し、結果がその発行者に一致することを確認します。
4. カテゴリと発行者のフィルターを組み合わせ、issue と承認した計画に沿って結果が表示されることを確認します。複数カテゴリに対応している場合は、合意した組み合わせの動作も確認します。
5. ゲームが見つからない組み合わせを試して、空の状態を確認します。フィルターを解除またはリセットして、すべてのゲームが表示されることを確認します。
6. 確認が終わったら、次のプロンプトで、このセッションに対して起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンでもこのセッションを使う

フィルター機能の PR をまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後はセッションをそのままにし、次のレッスンで同じセッションに戻ります。
